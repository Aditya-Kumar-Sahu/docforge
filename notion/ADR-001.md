# ADR-001: Why PostgreSQL + pgvector over Pinecone

**Date:** 2023-10-27
**Status:** Accepted

## Context
DocForge requires storing codebase embeddings to facilitate context retrieval for the LangChain pipeline. We need a vector database to search against abstract syntax trees and file chunks. The choices were a managed vector DB (Pinecone) or a Postgres extension (pgvector).

## Decision
We chose **PostgreSQL 16 + pgvector**.

## Rationale
1. **Simplified Infrastructure:** We already need PostgreSQL for transactional data (users, repos, endpoints). Adding pgvector means we don't need to add and maintain a separate stateful service in Phase 0.
2. **ACID Compliance:** We can tie endpoint deletions and repo uninstalls to chunk deletions natively via Foreign Keys and Cascade rules.
3. **Cost Efficiency:** Pinecone's base tier introduces minimum monthly costs, whereas pgvector allows us to use Azure Managed Postgres for all data needs under a single predictable cost structure.
4. **Scale:** pgvector's IVFFlat and HNSW indexes are more than sufficient for the MVP scale of 50,000+ chunks.

## Consequences
- Requires using Docker images with pgvector pre-installed for local development (`ankane/pgvector` or official `pgvector/pgvector`).
- Alembic migrations must explicitly create the `vector` extension.
